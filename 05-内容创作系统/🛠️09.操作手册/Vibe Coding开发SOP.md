# Vibe Coding 开发SOP

> 适用于：Obsidian插件开发、Web项目、脚本工具、任何用AI协作写代码的场景。
> 核心原则：**你负责边界和验收，AI负责体力活。**
> 来源：姜学长vibe coding方法论 + Boris Cherny（Claude Code创始人）经验 + 实战踩坑，2026-03-18整理。

---

## 第零阶段：喂弹药（给AI装上正确的知识）

在说第一句话之前，先做两件事：

### Step 0.1：喂相关文档

AI会编造不存在的API。开工前必须把相关文档喂进去：

| 项目类型 | 必喂文档 |
|---------|---------|
| Obsidian插件 | Obsidian Plugin API文档、现有插件的main.ts作为参考 |
| Web项目 | 框架官方文档、UI库文档 |
| 脚本工具 | 目标平台API文档 |

> **踩坑教训**：AI写了不存在的Obsidian API方法，debug了2小时才发现是API本身就不存在。喂文档10秒钟，省2小时。

### Step 0.2：告诉AI先规划再动手

**每个任务开头说这句话：**

> "先别写代码。告诉我你打算怎么改、改哪些文件、每个文件改什么，我确认了再动手。"

这是Boris Cherny的核心建议——Plan模式先行，输出质量提升2-3倍。

## 第一阶段：定图纸（写代码前先画清楚）

### Step 1：导需求（像聊天一样）

不用写正式文档，直接跟AI聊：
- 这个东西要解决什么痛点？
- 谁来用？（自己用 / 学员用 / 公开发布）
- 核心功能是什么？（最多3个）
- 理想的使用场景长什么样？

> **场景举例**：「我想做一个Obsidian插件，在聊天窗口右键可以把选中的文字一键发到公众号草稿箱」

### Step 2：让AI出PRD.md

让AI把聊天内容整理成结构化PRD，必须包含：

```
## 功能列表
- [ ] 功能1：xxx
  - 验收标准：做到什么算完成
- [ ] 功能2：xxx
  - 验收标准：xxx

## 用户流程
1. 用户做xxx → 2. 系统做xxx → 3. 结果是xxx

## 页面/界面清单
- 设置页：xxx
- 主界面：xxx
```

**关键**：每个功能必须有**验收标准**。没有验收标准，AI会越写越发散。

> 示例验收标准：「登录成功 = 跳转到主页 + 显示用户名；登录失败 = 显示错误提示 + 不锁定账号」

### Step 3：确定视觉/交互参考

- 找2-3个参考产品/插件的截图或链接
- 确定整体风格（简约 / 功能优先 / 跟现有插件统一）
- 确定基本布局（导航栏位置、按钮样式、配色）

> 目的：防止AI一边写功能一边推翻UI，来回返工。

## 第二阶段：打地基（明确边界和约束）

### Step 4：回答三个问题

| 问题 | 为什么重要 |
|------|-----------|
| 本地自用还是要上线公开？ | 决定是否需要安全加固、错误处理 |
| 有没有用户数据/支付/隐私？ | 决定是否需要加密、合规 |
| 性能和成本有没有上限？ | 决定技术选型和架构复杂度 |

> **常见场景**：Obsidian插件 = 本地运行 + 调用外部API + 有API Key安全问题

### Step 5：锁定技术栈

原则：**不追新，追可控。**

- 选资料多、社区活跃的技术（AI不容易瞎编）
- 选有官方文档和清晰示例的
- 选能跑测试、能review的

> **默认技术栈**：TypeScript + Obsidian Plugin API + esbuild。已经跑通的就别换。

### Step 6：让AI出架构草案（arc.md）

让AI输出：
- 目录结构怎么分
- 核心模块有哪些
- 数据模型长什么样
- 哪些逻辑必须在哪一层

**注意**：这是**草案**，允许迭代。但每次改架构必须记录原因。

## 第三阶段：立规矩（给AI设护栏）

### Step 7：固化三个文档到项目根目录

| 文件 | 内容 | 更新频率 |
|------|------|---------|
| `PRD.md` | 需求 + 验收标准 | 需求变了就更新 |
| `arc.md` | 架构 + 目录结构 | 架构改了就更新 |
| `project.md` | 当前进度 + 已知问题 + 下一步 | 每次大改动必更新 |

> **这三份就是AI的全局上下文。** 不更新 = AI按旧世界观写新代码 = 灾难。

### Step 8：定开发规范 + 建参考资料

在项目根目录建 `RULES.md` 或写在 `CLAUDE.md` 里：

```
## 开发规范
- 必须用 TypeScript
- 组件命名：PascalCase
- 单个文件不超过 300 行
- 函数命名：动词开头（getXxx, handleXxx, renderXxx）

## 参考实现
见 /reference/ 文件夹下的标准实现
```

可以在 `/reference/` 放你认可的标准实现（按钮、表单、弹窗等），让AI照着写。

### Step 9：拉起安全带（Git + 质量闸门）

写第一行代码前：

```bash
git init
git add .
git commit -m "init: 项目初始化，PRD+架构+规范就位"
```

后续每完成一个小功能就提交一次。**Git是你的安全带，坏了随时回滚。**

## 开发中：5个关键点

### 关键点1：小步迭代MVP

**一次只做一个可验证的小切片。** 不要一口气让AI写一大堆。

```
切片顺序示例（Obsidian插件）：
1. 插件能加载，设置页能打开 → git commit
2. 设置页能保存API Key → git commit
3. 右键菜单能出现 → git commit
4. 点击后能调用API → git commit
5. API返回结果能显示 → git commit
```

每完成一个切片：跑一下 → 确认能用 → git commit。

### 关键点2：人类必须介入——主动拆分模块

不允许所有代码堆在一个文件里。AI会这么做（因为省事），但你必须拆：

- 一个文件一个职责
- 超过300行就考虑拆分
- 工具函数单独放 `utils/`

### 关键点3：禁止AI做主

**每次任务结尾加这句话：**

> "只改我点名的文件和范围，不要顺手重构，不要改UI风格，不要改无关逻辑。"

AI修一个按钮可能顺手重写整个页面。这句话是防火墙。

### 关键点4：死守安全底线

| 底线 | 做法 |
|------|------|
| API Key不进前端 | 用环境变量 / Obsidian设置页存储 |
| API Key不进Git仓库 | `.gitignore` 加上配置文件 |
| 服务端必须做鉴权 | 不信任前端传来的任何数据 |
| 用户输入必须校验 | 防注入、防XSS |

### 关键点5：科学应对报错

**判断信号不是轮数，是"有没有新证据出现"。** 如果AI连续两轮修bug但没有产生任何新信息（没加日志、没缩小范围、只是换种写法猜）→ 立即停掉。

正确动作三步：
1. **最小复现**：把问题缩到最小输入
2. **加日志**：打印关键变量和分支走向
3. **拿证据再修**：把日志结果给AI，让它基于证据修

实在不行 → `git checkout` 回滚到上一个稳定点，别让它扩大损失。

### 关键点6：管理上下文（防AI变蠢）

对话越长，AI越蠢。这是vibe coding最隐蔽的翻车点。

**什么时候开新对话：**
- 超过20轮对话
- AI开始重复犯已经修过的错
- 切换到完全不同的模块

**新对话怎么快速恢复上下文：**
```
把这三个文件读一下，然后我们继续开发：
1. PRD.md
2. arc.md
3. project.md
```

**大文件怎么处理：**
- 超过300行的文件不要整个丢给AI
- 只给相关片段 + 说清楚这个片段在文件的什么位置
- 告诉AI"这个文件总共X行，我给你的是第Y-Z行"

### 关键点7：手动测试检查清单

"跑一下确认能用"不够。每个切片完成后，至少过一遍：

- [ ] 正常输入能用吗？
- [ ] 空输入会崩吗？
- [ ] 超长输入会崩吗？
- [ ] 网络断了/API挂了会怎样？（如果有网络请求）
- [ ] 设置页的配置改了，功能会跟着变吗？

## 快速检查清单

### 开工前（2分钟过一遍）

- [ ] 相关文档喂给AI了吗？（API文档、参考代码）
- [ ] PRD.md 写了吗？每个功能有验收标准吗？
- [ ] 技术栈确定了吗？不追新追可控？
- [ ] arc.md 架构草案出了吗？
- [ ] Git初始化了吗？
- [ ] 开发规范写了吗？

### 每个切片开工时（10秒）

- [ ] 跟AI说"先别写代码，先告诉我你打算怎么改"了吗？

### 每个切片完成后（1分钟）

- [ ] 正常输入跑通了吗？
- [ ] 边界情况测了吗？（空输入、超长、断网）
- [ ] git commit了吗？
- [ ] project.md更新了吗？

### 遇到bug时

- [ ] AI这一轮产生了新证据吗？没有 → 停
- [ ] 加日志了吗？拿到证据了吗？
- [ ] 实在不行 → git回滚了吗？

### 对话变长时

- [ ] 超过20轮了吗？AI开始重复犯错了吗？→ 开新对话
- [ ] 新对话喂了PRD+arc+project三个文件了吗？

# Skill 迭代（v2.1）

把测试失败的 Skill 修好，留下可追溯的迭代记录，推动它从草稿 Skill 走向资产 Skill。你是维修师：外科手术式修改者，不是重建者。

两个核心信念：

1. **先定位，再改一个地方，别推倒重来。** 一次改多处，复测通过了不知道哪一刀起效，失败了更不知道哪一刀砍坏。
2. **改动要能泛化，不要过拟合。** 目标是千百次不同输入下都可用。针对单个用例的死规则，宁可换更通用的写法。

## 输入要求

三样缺一先追问：被改 Skill 的完整内容、至少一条失败情况（Skill测试 报告最佳；口头描述也可，但先补问：当时输入了什么、期望什么、实际得到什么）。

## 工作流程

### 第 1 步：定位病灶

对照 Skill测试 的失败归因表，把症状映射到九块中的具体位置（description 触发话术 / 排除边界 / 工作流程 / 检查点 / 输出格式 / 禁区 / 交接包 / 缺块补块）。特别注意两类：

- **冲突类失败**（多 skill 抢入口）：单改本 skill 的 description 不够时，说明涉及系统边界，报 `Skill治理` 统一裁决，不自行给别的 skill 动刀
- **通道类失败**（可自动化却写成手工流程）：优先把 CLI / API / MCP / scripts 机器通道写进流程；浏览器只作兜底并写明原因

给出一两句原因判断，**向用户确认定位后再动刀**。

### 第 2 步：改一个地方

- 只改定位到的那一处；顺手看到的其他问题记入"待办"，本轮不动
- 优先用更清晰的写法替代加规则；确需加规则时自查：这条规则对其他输入也成立吗？只对眼前用例成立的属于过拟合，换通用写法
- 遵守原 skill 的九块结构和风险等级约定，不引入新的越权能力

### 第 3 步：写迭代记录

每轮填一行（模板见 `references/迭代记录模板.md`）：失败用例 / 症状 / 原因判断 / 修改位置 / 修改内容 / 复测结果 / 新增测试。本轮失败用例固定收编为回归测试。涉及执行方式时追加：推荐通道 / 浏览器是否兜底 / 通道调整原因。

### 第 4 步：交回复测 + 管理版本

输出修改后完整 Skill + 修改对比，指引交回 **Skill测试** 复测（本轮失败用例 + 全部历史回归用例 + 通道回归）。复测通过后按版本阶梯提升：

| 版本 | 含义 | 晋升条件 |
|---|---|---|
| v0.1 | 草稿版 | 刚造出来 |
| v0.5 | 内测版 | 三类测试首次全通过 |
| v1.0 | 可用版 | 真实业务连续使用无失败，过上线清单 |
| v1.x | 修正版 | 每轮迭代 +0.1 |
| v2.0 | 重构版 | 结构性改写（需用户明确批准，交 Skill生成 执行） |

v1.0 上线清单见 `references/上线清单.md`。

## 检查点

- 病灶定位 → 用户确认后再改
- 修改涉及禁区放宽 → 逐条确认，默认不放宽
- 用户要求一次改多处或推倒重写 → 陈述代价（无法归因、丢失已验证部分）后再确认；重写属 v2.0 重构，交 Skill生成
- 升版本 → 复测通过证据在手才升
- 修改落盘后 → 同步 `.agents/skills` 镜像，重大改动更新技能中心索引

## 下游依赖

- 上游：**Skill测试** 的测试验收报告
- 下游：改完交回 **Skill测试** 复测，形成"测→改→复测"闭环；系统性问题移交 **Skill治理**

## 输出格式

1. 原因判断：症状 → 病灶块 + 依据
2. 修改对比：改动处原文和新文（只应有一处）
3. 迭代记录一行
4. 执行通道判断
5. 复测指引：本轮失败 + 历史回归 + 通道回归
6. 版本建议

## 禁区边界

- 一轮不改第二个地方（待办可以记，刀不能落）
- 不推倒重写，除非用户了解代价后明确批准
- 不删除或篡改历史迭代记录
- 不为通过眼前用例写死过拟合规则
- 不在无复测证据时宣布"修好了"或升版本
- 不擅自修改其他 skill 来解决冲突（报 Skill治理）

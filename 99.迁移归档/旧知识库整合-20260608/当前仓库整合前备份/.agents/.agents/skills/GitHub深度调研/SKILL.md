# GitHub 深度调研 Skill

## 角色

你是用户的技术选型侦察兵。用户想找GitHub上能用的东西时，你的任务是**多路并行深度搜索，筛出真正有用的，按优先级排好，存成报告**。

## 触发场景

- 用户说"有没有现成的XXX"
- 用户说"去GitHub搜一下"
- 用户想实现某个功能，需要先看看有没有开源方案
- 用户说"别造轮子""找找有没有能用的"
- 需要做技术选型对比
- 想扩充MCP Server / Skills / Obsidian插件

## 执行流程

### 第1步：明确搜索方向

从用户的需求中提取搜索方向。如果用户给了明确方向，直接用；如果用户说"全面搜一下"，按以下默认方向拆分：

**默认搜索方向（可按需裁剪）：**
1. MCP Servers — 能通过MCP协议接入Claude Code的工具
2. Claude Code Skills / Hooks — 现成的技能包和自动化钩子
3. Obsidian 插件/集成 — 增强知识库能力的插件
4. 内容自动化 — 多平台发布、数据采集、视频制作
5. 用户指定的特定方向

### 第2步：多路并行搜索

**关键原则：每个方向至少用3组不同关键词搜索，交叉验证，不是随便搜一下就交差。**

为每个方向启动一个Agent子任务（`run_in_background=true`），每个Agent执行：

1. 用WebSearch搜索3-5组不同关键词组合
2. 搜索策略：
   - 英文关键词为主（GitHub项目名通常是英文）
   - 加"awesome"前缀找精选列表（如"awesome mcp servers"）
   - 加"github"+"stars"找热门项目
   - 加具体平台名找垂直工具（如"wechat publish github"）
   - 加年份找最新项目（如"2026"）
   - 中文关键词补充搜（如"公众号 自动发布 github"）
3. 对每个找到的项目记录：
   - 项目全名和GitHub URL
   - Star数（判断社区认可度）
   - 一句话说明干什么
   - 最近更新时间（判断是否活跃）
   - 对用户的具体价值（不要泛泛而谈，要结合用户的系统说清楚能替代什么、增强什么）

**Agent prompt模板：**

```
你是GitHub技术调研专家。请用WebSearch深度搜索以下方向的GitHub项目：

方向：{具体方向描述}

搜索关键词（至少用以下关键词各搜一次）：
{3-5组关键词}

用户背景（用于判断价值）：
- 用Obsidian管理知识库（记忆系统+内容创作系统）
- 用Claude Code + 60+自定义Skills做AI原生内容创作
- 有14个AI员工（OpenClaw多Agent系统）
- 需要自动发布到公众号/视频号/抖音/小红书/X
- 用Playwright做浏览器自动化
- 用MCP做各种集成
- 核心工作：写公众号文案、做短视频、卖知识付费课程
- 非程序员，需要傻瓜化的工具
- 已有工具：Playwright CDP视频发布、Coze热点收集工作流、飞书lark-cli

对每个项目记录：项目名、GitHub URL、Star数、一句话说明、对用户的具体价值。
只返回真正有用的项目，不要凑数。按"对用户价值从高到低"排序。
```

### 第3步：整合去重+分级

等所有Agent返回后，整合结果：

1. **去重**：不同Agent可能搜到同一个项目，合并
2. **交叉验证**：多个Agent都提到的项目优先级提升
3. **按价值分级**：

| 级别 | 标准 | 说明 |
|------|------|------|
| 🔴 P0 | 直接解决核心痛点 | 今天/本周就能用，ROI最高 |
| 🟡 P1 | 显著提升效率 | 本周研究，下周接入 |
| 🟢 P2 | 特定场景有用 | 评估后接入 |
| 🔵 观望 | Star太低或非刚需 | 收藏不行动 |

**分级判断依据：**
- Star数 > 1k 且最近3个月有更新 → 基本可信
- Star数 < 100 → 需看源码质量再决定
- 直接解决"当下每时每刻"里的P0/P1任务 → 提升到P0
- 替代现有手动操作 → 至少P1
- 和现有工具功能重叠 → 降级或标注"可替代XXX"

- 存档后告知用户文件位置

### 第5步：给出行动建议

报告最后，用口语化的方式告诉用户：
1. 最值得先搞的1-3个是什么
2. 为什么（结合当前痛点）
3. 要不要现在就研究怎么接入

## 执行规则

1. **多路并行是铁律**：至少2路Agent同时搜，方向多时3-4路。串行搜效率太低
2. **每路至少3组关键词**：避免单一关键词遗漏。英文为主+中文补充
3. **只返回有用的**：不凑数，宁可报告短也不灌水
4. **Star数要标**：这是判断项目可靠性的第一指标
5. **结合用户系统说价值**：不要说"可以提升效率"这种废话，要说"可以替代你现在手动发小红书的步骤"
6. **已有工具要对比**：如果搜到的工具和用户已有的功能重叠，明确说"你已经有XXX在做这件事，这个的优势是XXX"
7. **接入难度要标**：⭐=装个插件完事，⭐⭐=需要配置，⭐⭐⭐=需要部署服务器
8. **反造轮子检查**：搜到好东西时，先Grep知识库看用户是不是已经有类似的skill/工具，有就标注

## 禁止行为

1. ❌ 不要只搜一次就交差，每个方向至少3组关键词
2. ❌ 不要列一堆"可能有用"的项目充数
3. ❌ 不要忽略Star数极低（<10）的项目质量风险
4. ❌ 不要推荐已经停止维护（>1年无更新）的项目，除非无替代
5. ❌ 不要只说"这个很好"，要说清楚好在哪、怎么接入、替代什么
